# Схема данных

`schema.sql` — начальная миграция для пустой PostgreSQL 16.
Compose применяет её через docker-entrypoint-initdb.d только при первом старте
пустого volume. Повторное изменение SQL не обновляет существующую базу:
дальнейшие изменения оформляются отдельными миграциями в `migrations/`.
`erd.puml` отражает сущности и связи, полный набор полей и ограничений — в SQL.

Владение: student → document → карточки, задания и ответы. Приложение проверяет
владельца документа при каждом запросе; наличие FK не заменяет авторизацию.
Составные FK не позволяют связать карточку с chunk/job другого документа.
Приложение также проверяет точную цитату, соответствие offsets тексту и
добавляет расписание только принятой карточке. `active` означает accepted
с расписанием, отдельного статуса active в БД нет.

Текст хранится в PostgreSQL для небольшого MVP. PDF/OCR и файловое хранилище
пока не реализованы. Удаление студента каскадно удаляет его учебные данные;
политика резервных копий и сроки хранения требуют согласования.
Идентификаторы UUID генерирует приложение. `updated_at` обновляется явно.

Проверка ограничений без сохранения тестовых данных (PowerShell, после запуска):

```powershell
Get-Content -Raw database/check-schema.sql | docker compose -f compose.dev.yml exec -T db psql -U bpta -d bpta -v ON_ERROR_STOP=1
```

Проверяются 10 условий: источник и job другого документа, неверный статус job,
формула без выражения/обозначений, формула у short_qa, не-массив variables,
повтор номера chunk, корректная formula и partial job, partially_correct с
метаданными самооценки, каскадное удаление владельца.

Полный изолированный тест (создаёт новую БД и удаляет только свой тестовый volume):
`python scripts/check-compose.py`. Существующая dev-БД не используется.

## Соответствие AI-контракту

Канонический API: `api/openapi.yaml`. UUID `source_chunk.id` — внутренний ключ;
API `chunk_id` — положительный `sequence_no` внутри конкретного document_id.
Приложение преобразует пару `(document_id, chunk_id)` в UUID; номер без документа
никогда не используется для авторизации. `source_locator` и page_number
сохраняются в chunk; карточка получает их через FK, а не дублирует.

`answer` → `reference_answer`, `source_fragment` → `source_quote`,
`approval_status=pending` → `status=draft`. Принятие и удаление — отдельные
действия пользователя. `card_type`, `formula`, `variables` хранятся явно;
JSON-массив обозначений дополнительно валидирует приложение по OpenAPI.
Статусы generation_job и review.model_result совпадают с AI API.
`requires_self_check` и confidence не теряются при сохранении; результат
самооценки хранится отдельно от результата модели.

В текущей лабораторной это контракт хранения, а не реализация импортирующего API.
Не изменять действующий volume этой схемой автоматически: старая версия требует
отдельной миграции/backup. `schema.sql` — стартовая схема только пустой БД.

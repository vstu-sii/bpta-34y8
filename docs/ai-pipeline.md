# AI-пайплайн генерации и проверки учебных карточек

## 1. Назначение и границы

Пайплайн преобразует текст из TXT, MD или текстового PDF в проверяемые учебные карточки. Для каждой карточки сохраняются тип, вопрос, ответ, точная цитата, положение в документе и статус ручного одобрения. Для карточек типа `formula` дополнительно сохраняются формула и расшифровка переменных.

В MVP используется управляемый workflow: порядок шагов задаёт код, а модель выполняет только ограниченные задачи генерации и семантической оценки. Модель не получает самостоятельного доступа к базе данных, файлам, API-ключам или внешним инструментам.

Основная модель — Ollama Cloud `gemma4:31b`. Резерв — локальная Ollama `qwen3.5:4b`.

## 3. Последовательность обработки

| Этап | Вход | Выход | Контроль качества |
|---|---|---|---|
| 1. Приём документа | TXT, MD или PDF | `document_id` и файл | Тип, размер, отсутствие пустого файла |
| 2. Извлечение | Файл | Текст по страницам или блокам | Пустые страницы и ошибки парсера фиксируются |
| 3. Очистка | Извлечённый текст | Нормализованный текст | Удаляются NUL и лишние пробелы, сохраняются абзацы |
| 4. Разбиение | Текст и номера страниц | Фрагменты до 5 000 символов | Каждый фрагмент получает `chunk_id` и `source_locator` |
| 5. Формирование промпта | Один фрагмент | System + user prompt | Версия промпта фиксируется в журнале |
| 6. Генерация | Один промпт | Текстовый ответ модели | Тайм-аут, код HTTP, задержка и токены записываются |
| 7. Разбор JSON | Текст модели | Объект `cards` | Запрещён дополнительный текст; допустимо снятие Markdown-ограды |
| 8. Валидация | Сырые карточки и исходный фрагмент | Принятые карточки и причины отказа | Проверяются тип, поля, цитата, формула и переменные |
| 9. Дедупликация | Все принятые карточки документа | Уникальный набор | В MVP — точное сравнение нормализованных вопросов |
| 10. Сохранение | Валидные карточки | `approval_status=pending` | До ручного одобрения карточка не участвует в повторении |

### Проверка свободного ответа

Проверка ответа использует отдельный короткий запрос:

1. backend передаёт вопрос, эталон, точную цитату, 1–4 обязательных смысловых пункта и ответ студента;
2. модель возвращает `correct`, `partially_correct` или `incorrect`, а также найденные пункты, пропуски, фактические ошибки и уверенность;
3. JSON проходит проверку схемы и допустимых статусов;
4. при низкой уверенности выставляется `requires_self_check=true`: пользователю показываются эталон и объяснение, но решение модели не считается окончательным;
5. несогласие пользователя записывается как `grade_disputed` и становится материалом для eval-набора.

## 4. Промпты и структурированный выход

Промпт состоит из двух частей:

1. системная инструкция задаёт три типа карточек, приоритет типа `formula`, запрет внешних фактов и запрет выполнять инструкции из документа;
2. пользовательская часть содержит положение фрагмента, лимит карточек, JSON Schema и текст внутри явных границ `<SOURCE>...</SOURCE>`.

Обязательные поля результата:

```json
{
  "cards": [
    {
      "card_type": "short_qa | summary | formula",
      "question": "Вопрос",
      "answer": "Эталонный ответ",
      "source_fragment": "Точная цитата",
      "formula": null,
      "variables": []
    }
  ]
}
```

Ollama Cloud пока не поддерживает принудительные structured outputs. Поэтому JSON Schema передаётся модели как текст, а доверие к результату появляется только после локального парсинга и валидации. Источник: [Ollama Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs).

## 5. Границы контекста

### Модель видит

- системный промпт и его версию;
- один фрагмент длиной не более 5 000 символов;
- `source_locator` текущего фрагмента;
- JSON Schema ответа;
- для оценки ответа: вопрос, эталон, цитату и ответ студента.

### Модель не видит

- API-ключ Ollama;
- полный исходный файл и соседние фрагменты;
- персональные данные пользователя, если они не содержатся в самом документе;
- базу данных, очередь повторений и карточки других пользователей;
- ранее созданные карточки других фрагментов;
- системные журналы и внутренние причины ошибок;
- внешние сайты и инструменты.

Следствие: межстраничные связи и смысловые дубли нельзя надёжно обработать внутри одного модельного вызова. Их обрабатывает отдельный этап после объединения результатов.

## 6. Точки контроля качества

### До модели

- разрешены только TXT, MD и PDF;
- пустой файл и документ без извлечённого текста отклоняются;
- фрагменты имеют стабильные идентификаторы и привязку к странице;
- текст документа считается недоверенным и не становится системной инструкцией.

### После модели

- ответ должен быть одним JSON-объектом;
- `cards` должен быть списком не более чем из шести элементов на фрагмент;
- допустимы только `short_qa`, `summary`, `formula`;
- вопрос, ответ и `source_fragment` не могут быть пустыми;
- `source_fragment` должен находиться в исходном фрагменте после нормализации пробелов;
- карточка с выражением вида `X = ...` обязана иметь тип `formula`;
- `formula` должна встречаться в источнике, а `variables` не должен быть пустым;
- карточки с одинаковыми нормализованными вопросами удаляются;
- итоговая карточка получает `pending`, а не автоматически `accepted`.

### Ручная приёмка

Студент видит вопрос, ответ, тип, страницу и цитату. Он может принять, исправить или удалить карточку. Только принятая карточка переходит в активную колоду.

## 7. Логирование и наблюдаемость

Для каждого запроса записываются:

- `request_id`, `job_id`, `document_id`, `chunk_id`;
- модель, endpoint-класс (`cloud` или `local`) и `prompt_version`;
- номер попытки, HTTP-статус и категория ошибки;
- `latency_ms`, `prompt_eval_count`, `eval_count`;
- количество полученных, принятых и отклонённых карточек;
- коды причин отклонения;
- число удалённых точных и смысловых дублей;
- итоговый статус фрагмента и задания.

API-ключ, полный ответ студента и полный текст документа в технические логи не записываются. Для отладки допускаются идентификатор и хеш фрагмента; сырые данные хранятся отдельно с ограничением доступа и сроком удаления.

## 8. Ошибки и деградация

| Ситуация | Реакция |
|---|---|
| Тайм-аут, HTTP 429 или 5xx | Повтор с экспоненциальной задержкой, не более двух попыток |
| Ошибка авторизации 401/403 | Остановить задание и сообщить об ошибке конфигурации |
| Некорректный JSON | Один ограниченный повтор; затем пропустить фрагмент и сохранить причину |
| Карточка не прошла проверку | Не сохранять как готовую; зафиксировать код отказа |
| Облачная квота исчерпана | Переключить новые фрагменты на локальную `qwen3.5:4b` |
| Локальная модель недоступна | Оставить документ в очереди или предложить ручное создание |
| Часть фрагментов завершилась ошибкой | Сохранить успешные результаты и показать неполное покрытие |

Переключение модели не меняет формат карточки, валидатор или статус ручной приёмки.

## 9. RAG и ограниченный агент

RAG не нужен для первичного полного прохода: при создании полной колоды должны быть просмотрены все фрагменты. Он добавляется для тематических запросов и библиотеки документов. Индекс хранит `document_id`, `chunk_id`, текст, страницу и embedding; найденные фрагменты проходят тот же генератор и валидатор.

Агент не управляет основным конвейером. Разрешён только ограниченный цикл исправления отклонённой карточки:

1. получить карточку и коды ошибок;
2. выполнить не более двух попыток исправления;
3. каждый раз вернуть результат в тот же валидатор;
4. при повторном отказе передать карточку человеку.

## 10. Критерии готовности пайплайна

- диаграмма PlantUML компилируется;
- один фрагмент не превышает заданную границу;
- каждый результат связан с `document_id`, `chunk_id` и страницей;
- невалидный JSON и неподтверждённые цитаты не попадают в колоду;
- токены и задержка доступны в журнале;
- облачная и локальная модели возвращают один контракт;
- карточки сохраняются только со статусом `pending`;
- ошибки одного фрагмента не уничтожают результаты остальных.

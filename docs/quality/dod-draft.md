# Definition of Done (DoD) — Lab 2 и следующие этапы

**Проект:** «Карточки для повторения из конспекта»  
**Ответственный за документ:** Quality & Safety  
**Версия:** 2.0 (15.10.2026)  
**Статус:** Draft; командное согласование ещё требуется

## 1. Для чего нужен DoD

DoD — список условий, по которым команда может **доказать** готовность результата: фактом, числом или ссылкой на артефакт. Формулировка «вроде работает» не является доказательством.

Не смешиваем три состояния:

- **Документ подготовлен:** написаны критерии, план и примеры.
- **Критерий согласован:** команда приняла его через обсуждение/PR.
- **Критерий выполнен:** проверка проведена и сохранены доказательства.

Отмечать чекбокс выполнения можно **только после проверки**, а не потому, что критерий описан. Для лабораторной №2 отделяем подготовку документации от последующих проверок функционирующей системы.

## 3. DoD генерации карточек (для этапа реализации)

- [ ] Система принимает текст конспекта **и** вопросы к зачёту.
- [ ] Для вопроса с подтверждаемым ответом выдаёт карточку с непустыми `question` и `answer`.
- [ ] Содержание карточки подтверждается конкретным фрагментом конспекта.
- [ ] Если ответа нет, система возвращает «недостаточно данных», не придумывая ответ.
- [ ] Конфликтующие сведения помечаются для проверки, а не уверенно выдаются как истина.
- [ ] Смысловые дубли не превышают согласованный порог.
- [ ] Результаты теста сохранены; известны версия системы и исходные данные.

**Доказательства:** входы, выходы, ссылки на кейсы и результаты Q1/Q4/Q5 из `success-criteria.md`.

## 4. DoD Golden Dataset

- [ ] Создан `data/golden_dataset/golden-dataset.json` с валидным JSON.
- [ ] Зафиксированы **30–50 контрольных случаев**; список включает положительные и отрицательные примеры.
- [ ] В каждом случае есть `id`, `source`, `input_text`, `exam_question`, `expected_action`, `question`, `reference_answer`, `category`, `version`; для `skip` ответ и карточка могут быть `null`.
- [ ] Для `skip` указан `skip_reason`; для проверки ответов используется массив `student_answers`.
- [ ] Для оценивания подготовлено не менее **20 размеченных ответов**, включая минимум 10 `accepted` и 10 `rejected`.
- [ ] ID уникальны, все источники допустимы, материалы обезличены.
- [ ] Спорные эталоны согласованы или отдельно помечены как `needs_review` до эксперимента.
- [ ] Набор имеет версию и фиксируется коммитом; основные эталоны нельзя незаметно менять после прогона.

**Доказательства:** ссылка на JSON, число случаев по категориям, результаты схемной проверки, SHA коммита.

## 5. DoD качества и оценки свободных ответов

- [ ] Карточки прогнаны на неизменной версии Golden Dataset.
- [ ] Рассчитаны Q1–Q5 с числителями и знаменателями.
- [ ] При наличии функции проверки свободных ответов рассчитана Q3 (accuracy) и матрица ошибок.
- [ ] Проверены перефразирования, неправильные ответы и вопросы без ответа в конспекте.
- [ ] Зафиксированы среднее время, p95 и число прогонов; измерение проводится на описанном типе входа.
- [ ] Зафиксированы расход токенов и стоимость; целевой предел стоимости обсуждён после выбора модели.
- [ ] Критические ошибки перечислены и разобраны; итоговая приёмка не проходит с необработанными критическими дефектами.
- [ ] Для повторного запуска указаны SHA коммита, модель, версия промпта, версия набора и конфигурация.

**Доказательства:** будущий `docs/quality/evaluation-report.md`, логи/таблицы без личных данных, примеры ошибок. **Отчёт сейчас не создан** — его нельзя отмечать выполненным.

## 6. DoD безопасности

- [ ] В опубликованных тестовых материалах нет личных и конфиденциальных данных.
- [ ] Для каждого источника указано происхождение и право использования.
- [ ] Инструкции, найденные внутри конспекта, рассматриваются как данные и не меняют правила работы системы.
- [ ] Когда конспекта недостаточно, система не добавляет факты «из памяти» без явного указания пользователю.
- [ ] Неподдерживаемые источники (например, сканы и видео, если функция ещё не реализована) не объявлены поддерживаемыми.
- [ ] Ключи API, токены и закрытые материалы не попали в Git и в отчёты.

**Доказательства:** отчёт о ручной проверке, тесты негативных случаев и проверка содержимого коммита.

## 7. Интервальное повторение — отдельная проверка продукта

Повторение — часть целевого поведения продукта из README, но подготовка документации Lab 2 **не означает**, что оно уже реализовано.

Если команда включает эту функцию в текущую итерацию, дополнительно проверяется:

- [ ] После ответа студента сохраняется результат оценки и дата следующего повторения.
- [ ] Расписание вычисляется по описанному, детерминированному правилу; правило и версия зафиксированы.
- [ ] Проверены хотя бы два сценария: успешный ответ и неправильный ответ; их влияние на интервал отличается согласно выбранному алгоритму.
- [ ] Повторная проверка состояния после перезапуска не теряет историю.

**Доказательства:** описание алгоритма, входные/выходные примеры и тесты. До включения в объём лабораторной эти условия считаются **открытым продуктовым решением**, а не автоматически обязательными пунктами Lab 2.

## 8. Процесс принятия решения при отсутствии Product

1. Предложения оформляются в документах и PR с пометкой «предварительно».
2. AI Engineer подтверждает техническую реализуемость, Quality & Safety — проверяемость, Delivery — возможность воспроизведения и сдачи.
3. Команда фиксирует согласованное решение и владельца в обсуждении PR/issue.
4. Нерешённые вопросы остаются открытыми и не выдаются за утверждённые.

| Вопрос | Текущее предложение | Решение команды |
| --- | --- | --- |
| Обязательные входные данные | Текст конспекта + список вопросов | Ожидается |
| PDF, видео, сканы | Вне обязательного теста Lab 2 до реализации | Ожидается |
| Условия принятия свободного ответа | Смысловое соответствие, `accepted`/`rejected` | Ожидается |
| Порог стоимости | После выбора модели и базового прогона | Ожидается |
| Алгоритм и срок реализации повторений | Определить отдельно | Ожидается |

# Golden dataset v1.1.0

Владелец: Quality & Safety. Версия: 1.1.0, 2026-11-05.
Формат: UTF-8 JSON Lines, один объект на строку. Инструмент:
`python tools/quality/evaluate.py validate` и `score --predictions <file>`.
Схема: `schema.json`; frozen checksum и число случаев: `manifest.json`.

## Происхождение и ограничения

40 оригинальных синтетических случаев, без реальных конспектов и персональных
данных. Авторский текст создан для проверок, нет заимствований учебных материалов.
В v1.0.0 кириллица во всех 40 кейсах была необратимо заменена знаками `?`.
В v1.1.0 входы и эталоны заново составлены с помощью агента на тех же категориях
и ID; это новая версия, а не незаметная правка frozen набора. Статус каждого
эталона — `pending_human_review`: проверка человеком, независимая двойная разметка
и согласование Product ещё требуются. Это не результаты интервью.
Объём соответствует заданию 30–50, но мал для статистически устойчивого вывода
о качестве продукта: показывать счётчики, разброс повторов и ограничения.
Для пилота добавить ≥ 10 разрешённых реальных случаев отдельной версией набора.

## Состав

16 generate, 4 abstain, 20 evaluate. Ответы: 10 correct, 5 partially_correct,
5 incorrect. Бинарная проекция: 10 accepted и 10 rejected; partial не считается
полностью правильным. Есть определения, процессы, сравнения, 4 формулы,
шум/Unicode, отсутствие ответа, конфликт и 8 кейсов с недоверенными инструкциями/markup.
Нет отдельной задачи retrieval: MVP не использует векторный поиск. Контекст
всё равно оценивается: точная цитата, правильный chunk/locator/page и смысловая опора.

## Контракт и адаптер

- `input.source` → `SourceChunk` текущего `docs/api/openapi.yaml`.
- `generate`: передать chunk и вопрос в продуктовый workflow. Внутренний AI API
  сейчас не принимает `exam_question`; перенос вопроса должен быть явно согласован
  AI + Product. Нельзя незаметно дописывать вопрос к источнику как доказательство.
- `abstain`: ожидается отсутствие карточки по заданному вопросу; это результат
  продуктового адаптера, а не выдуманный статус внутреннего AI API.
- `evaluate`: поля `question/reference_answer/source_fragment/student_answer`
  и `expected.required_points` → `EvaluateAnswerRequest`; card_id задаёт адаптер.
- Метки совпадают с OpenAPI: `correct`, `partially_correct`, `incorrect`.
  Mapping в БД (`partial`) согласовать отдельно; сейчас это открытое расхождение.

В `generate` эталонная карточка — один допустимый ответ, а не требование буквального
совпадения вопроса/ответа. Дословной должна быть только цитата и формула;
перефразы проверяет человек по `required_points`, вопросу и источнику.
Для partial перечислены все существенные пункты: часть есть, часть отсутствует.
В кейсе 035 отсутствует ограничение «только после принятия», поэтому ответ partial.

## Формат записанных предсказаний

Одна строка на каждый из 40 ID, без неизвестных/повторённых/пропущенных ID.

```json
{"id":"GD-021","task":"evaluate","status":"correct"}
{"id":"GD-017","task":"abstain","cards":[]}
{"id":"GD-001","task":"generate","error":"provider_timeout"}
```

Для успешного generate: `cards` — массив объектов `Card` из OpenAPI, `reviews` —
массив такой же длины, каждый элемент содержит boolean `grounded`, `useful`,
`duplicate`, `critical_error`, `covers_question` и непустой текст `evidence`.
Проверяющий заполняет review после получения реального вывода, до подсчёта метрик.
Grounded — источник подтверждает весь ответ; useful — карточка проверяет нужное
знание; duplicate — та же мысль уже встречалась в наборе; covers_question —
вопрос покрыт; critical_error — ложный факт, способный ввести в заблуждение.
Рубрику нельзя заполнять автоматически из эталонов и выдавать за модельный прогон.
Структурно корректная цитата без смысловой опоры не получает grounded=true.

Ошибка сохраняется `error` вместо успеха. `score` возвращает ненулевой код,
если gate не достигнут, данные неполны или невалидны; при отсутствии review
выдаёт ERROR. Пустые ответы/ошибки не удаляются из знаменателя покрытия.

## Пополнение и версионирование

QS принимает новые кейсы через PR: ID, источник/право использования, UC,
ожидание и причина. Product проверяет полезность, AI — контракт и смысл,
второй проверяющий — эталон. Спорные кейсы обсуждать до frozen прогона.
Изменение эталона → новая версия и checksum; старые результаты не переписывать.
Разделить dev и holdout на уровне исходного документа при добавлении реальных данных.
Результаты хранить с SHA кода/набора/предсказаний, моделью и версией промпта.
